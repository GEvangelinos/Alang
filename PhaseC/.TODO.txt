// Q: any way to register a variable's type based on a max value?
//    For example if I say max 240 u8 is enough but if i say 13000 we need u16
//    or if i say 40000000 we need u32 — but change automatically based on max value

// A: Yes, you can do this using template metaprogramming and std::conditional_t.
//    The following code defines `SelectUInt<Max>` which resolves at compile time
//    to the smallest unsigned integer type that can hold `Max`.

#include <cstdint>
#include <type_traits>

template <std::uint64_t Max>
using SelectUInt = std::conditional_t<
    (Max <= UINT8_MAX),  std::uint8_t,
    std::conditional_t<
        (Max <= UINT16_MAX), std::uint16_t,
        std::conditional_t<
            (Max <= UINT32_MAX), std::uint32_t,
            std::uint64_t
        >
    >
>;

// Usage examples:
SelectUInt<240> a;        // resolves to uint8_t
SelectUInt<13000> b;      // resolves to uint16_t
SelectUInt<40000000> c;   // resolves to uint32_t
SelectUInt<1ULL << 40> d; // resolves to uint64_t

In the future, I should implement a fixpoint-style optimization framework for my compiler.
The idea is to run multiple optimization passes repeatedly, not just once.
This is important because one optimization can unlock new opportunities for another (or even for itself).
For example, a dead code elimination pass might expose redundant jumps,
or constant folding might simplify expressions enough for branch simplification to kick in.
So rather than relying on a single pass-through,
I should loop over all optimization passes and re-run them until no further changes are made to the IR.
This ensures that the IR is fully simplified and optimized.
It also aligns with how real-world compilers (like LLVM and GCC) perform multi-pass
optimizations using a fixed-point approach.
This isn't a priority now, but it will be necessary when the IR and optimizer become more complex.

example of an optimization pass loop:

bool changed;
do {
    changed = false;

    changed |= run_const_folding(ir);
    changed |= run_copy_propagation(ir);
    changed |= run_dead_code_elim(ir);
    changed |= run_branch_simplification(ir);
    changed |= run_jump_threading(ir);

} while (changed);

# Error Recovery and Heuristics for AlphaLanguage Parser (Mental Model)

This file summarizes the ideas we discussed for making error reporting in your Bison-based compiler
more professional (Clang/GCC style) and less chaotic.

---

## 1. General Philosophy
- **Parsers know validity, not intent**: Bison can tell you what tokens would be valid, but not what
  the programmer *meant*.
- **Heuristics bridge the gap**: Human compilers (Clang, GCC) add pragmatic rules to guess intent.
- **Incremental approach**: Handle the most common fixes first (missing `;`, missing `)`, missing `}`).

---

## 2. Heuristics Ideas
- If `;` is in the expected set, and the next token starts on a new line → prefer `;`.
- If two identifiers are on the same line with no operator → suggest `+` or another operator.
- If you just parsed a declaration → missing `;` is by far the most likely.
- If inside a parenthesized context → missing `)` is likely.
- Always rank tokens: (`;` > `)` > `}` > operators > others).

---

## 3. Lexer Context (Tracking Previous Tokens)
Extend your lexer context to keep track of current and previous token text and locations:

```cpp
struct LexerCtx {
    YYLTYPE curr_loc{};
    std::string curr_text;
    YYLTYPE prev_loc{};
    std::string prev_text;
};
```

In `yylex`:

```cpp
int yylex(YYSTYPE *yylval, YYLTYPE *yylloc, yyscan_t scanner, LexerCtx &ctx) {
    ctx.prev_loc = ctx.curr_loc;
    ctx.prev_text = ctx.curr_text;

    int tok = real_yylex(yylval, yylloc, scanner);

    ctx.curr_loc = *yylloc;
    ctx.curr_text = alpha_yyget_text(scanner);
    return tok;
}
```

This lets you say:
```cpp
if (semi_expected && ctx.curr_loc.first_line > ctx.prev_loc.last_line) {
    syntax_error = FMT::format(
        "error: expected ';' after `{}` (before `{}`)",
        ctx.prev_text,
        ctx.curr_text
    );
}
```

---

## 4. Using Expression / IR Tracking
- Store `last_expr_kind` and `last_expr_loc` when reducing expressions in Bison.
- Example: `ExprKind::Arithmetic`, `ExprKind::Boolean`, `ExprKind::Assignment`, etc.
- In error reporter, combine this with `expected_tokens`:
  - If last expr is arithmetic and the next token is an identifier on the same line → suggest `+`.
  - If last expr is boolean/assignment and the next token is on a new line → suggest `;`.

This makes diagnostics semantically aware.

---

## 5. GCC vs Clang Diagnostic Style
- **GCC**: "expected ';' before 'xyz' token"
- **Clang**: "expected ';' at end of declaration"
- To mimic Clang: map grammar rules (stmt, decl, expr) into phrases ("at end of declaration").
- To mimic GCC: use token names ("before 'xyz'").

---

## 6. Handling Different Cases
- **If 1 expected token**: phrase it cleanly ("expected ';' before 'xyz'").
- **If multiple expected tokens**: show the top suggestion, then a short list of others.
- **If >5 tokens**: truncate or just say "expected one of X, Y, Z".

---

## 7. Advanced Extensions
- **Token history buffer**: keep last N tokens in lexer context for richer diagnostics ("saw A, then B, then C").
- **Pretty-printer for tokens**: map YYSYMBOL names to readable ones (`YYSYMBOL_SEMICOLON -> ';'`, `YYSYMBOL_IDENTIFIER -> 'identifier'`).
- **Future idea**: integrate with quads (IR) → if last emitted quad is arithmetic, prefer operator fix.

---

## 8. Strategy for Implementation
1. Implement previous-loc tracking in lexer.
2. Special-case missing `;` using newline heuristic.
3. Add pretty token printer for clean messages.
4. Gradually add semantic-aware heuristics using `last_expr_kind`.
5. Optionally add token history buffer for context in notes.

---

This is how you move from a raw "Lookahead Correction algorithm dump" to **professional GCC/Clang-style diagnostics**.

104) Optimization patterns:

a = b+c;

produces an add to a temp of b+c;
and then an assignment of that temp to a.

here is the thing.. we have thought of ADD SUB, ... istruction as producers only..
and that the only way store a result is the ASSIGN Opcode..

but that simply aint true..

Opcode ADD.. can very well store stuff.. its result field is a store..
So.. we can find continuous chains and optimize them..

for example x= a+b; produces

quad#      opcode          result               arg1                 arg2                 label      line
---------------------------------------------------------------------------------------------------------------
1          add             _t0                  a                    b                    -          1
2          assign          x                    _t0                                       -          1

which can simply become
1          add             x                  a                    b                    -          1


of course this requires a post ir-generation step.. fine.. I like it..

By the way.. if we didnt have the ASSIGN opcode.. we could do stores (assignment)


with add lhs , rhs, 0... it would practically be the same..
