    Ohhh yes — this is the real compiler engineering pain: juggling multiple properties like is_lvalue, is_const, is_callable, is_assignable, etc., across dozens of rules… and trying to avoid a forest of flags.

    You’re right: storing 20 bools works, but it gets messy fast. Good news is — there are way more elegant ways to handle this.
     What You Want: Per-node attributes in a clean structure

    Instead of tracking separate bool is_lvalue_, bool is_const_, etc., scattered around, you define a single struct or object that bundles all semantic properties of an expression.
    Step 1: Define a unified "ExpressionInfo" struct

    struct ExprInfo {
        bool is_const = false;
        bool is_lvalue = false;
        bool is_callable = false;
        bool is_temp = false;

        ConstValue const_value;  // if known and is_const == true
        // Add more flags or enums as your language grows

        static ExprInfo make_const(ConstValue v) {
            ExprInfo info;
            info.is_const = true;
            info.const_value = v;
            return info;
        }

        static ExprInfo make_lvalue() {
            ExprInfo info;
            info.is_lvalue = true;
            return info;
        }
    };

    Now, any rule that produces an expression or term can return an ExprInfo.
     Step 2: Use this in your semantic functions
    Example in Bison:

    expr:
        INT {
            $$ = ExprInfo::make_const(ConstValue::from_int($1));
        }
    | ID {
            $$ = lookup_expr_info($1); // sets is_lvalue = true, etc.
        }
    | '-' expr {
            if (!$2.is_const)
                error("Unary '-' on non-const expr");
            $$ = ExprInfo::make_const(ConstValue::negate($2.const_value));
        }
    | lvalue {
            $$ = $1; // carries is_lvalue = true
        }

     Benefits of this system

        Scalable — you can add more flags later (e.g. is_reference, is_loop_var) without changing every rule

        Clean — you return one thing from each rule, not 3 booleans + value

        Composable — when combining subexpressions (e.g. in expr '+' expr), you can merge or check flags easily

        Safer — prevents mismatches like setting is_const without setting a value

     Bonus: Enums instead of bools?

    You could also use enum class ExprKind { Const, LValue, Temp, Unknown }, but that’s best when expressions are mutually exclusive, which yours are not — so struct + booleans is better.
     TL;DR

        Yes, avoid 20 loose booleans — that’s a trap.

        Instead, return a clean ExprInfo struct with all relevant flags + payload.

        It’s scalable, clean, and idiomatic for single-pass compilers.
